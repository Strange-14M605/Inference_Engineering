#### Q1 (Compute vs. Memory Bottleneck): Why is the Prefill phase of LLM inference compute-bound (high arithmetic intensity), whereas the Decode phase is memory-bandwidth bound (low arithmetic intensity)?

- **Your Answer:** *Prefill involves finding relationships between tokens through training on pre-existing data. Decode requires a fast forward pass relying on throughput over arithmetic latency.*
- **Senior MLE Evaluation:**
    - **Core Misconception to Clear Up:** **Prefill is NOT training!** Prefill is the very first step of *inference* when a user submits a prompt.
    - **Why Prefill is Compute-Bound (High Arithmetic Intensity):**
        - In Prefill, the model processes all \(N\) tokens of the input prompt **simultaneously in parallel**.
        - The core matrix operations are **Matrix-Matrix multiplications** (e.g., GEMM: \([N \times d] \times [d \times d]\)). Because \(N\) is large, the GPU performs thousands of mathematical operations (FLOPs) for every byte of weight data transferred from main GPU VRAM (HBM) into fast chip memory (SRAM/registers).
        - This high **Arithmetic Intensity** (\(\text{FLOPs} / \text{Byte}\)) fully saturates the GPU's Tensor Cores—making the hardware **Compute-Bound**.
    - **Why Decode is Memory-Bandwidth Bound (Low Arithmetic Intensity):**
        - In Decode, tokens are generated auto-regressively **one token at a time** (\(N=1\)).
        - To predict token #101, the GPU must load **all model weights** (e.g., 140 GB for a 70B FP16 model) from HBM into SRAM just to perform a **Matrix-Vector multiplication** (\([1 \times d] \times [d \times d]\)) for that single token step.
        - The arithmetic intensity is tiny (~1 FLOP per byte transferred). The GPU's compute cores sit idle 90%+ of the time, waiting for memory read buses to transfer weight bytes. Thus, Decode speed is governed strictly by **GPU Memory Bandwidth (GB/s)**.

> **A Senior MLE Answer:**
> 
> 
> *"Prefill processes the entire input prompt in parallel, performing Matrix-Matrix (GEMM) operations. This yields high arithmetic intensity (\(\text{FLOPs}/\text{Byte}\)), fully utilizing GPU compute units and making Prefill compute-bound. In contrast, the Decode phase generates tokens one by one (\(N=1\)), converting operations to Matrix-Vector (GEMV). To output a single token, the GPU must stream every model weight from HBM into SRAM, yielding low arithmetic intensity. Decode is therefore memory-bandwidth bound, limited by HBM transfer speeds rather than raw TFLOPS."*

#### Q2 (Latency Decomposition): How do Time-To-First-Token (TTFT) and Inter-Token Latency (ITL) map to the Prefill and Decode phases, and which model parameters dictate each metric?

- **Your Answer:** *Time-To-First-Token is part of decode phase and depends on input length. Inter-Token Latency is part of prefill phase and depends on model layers/parameters.*
- **Senior MLE Evaluation:**
    - **Core Adjustment:** Your mapping was inverted!
        - **TTFT (Time-To-First-Token)** maps directly to the **Prefill Phase**.
        - **ITL (Inter-Token Latency)** maps directly to the **Decode Phase**.
    - **Dictating Parameters:**
        - **TTFT (Prefill):** Measures the time from request submission until the very first output token appears. It is dictated primarily by **Prompt Context Length (\(N_{\text{prompt}}\))**, Attention matrix complexity (\(O(N^2)\) unless optimized), total model TFLOPS, and batch prefill size.
        - **ITL (Decode):** Measures the time between generating token \(i\) and token \(i+1\) (perceived streaming speed). It is dictated by **Model Parameter Size (total GB of weights to load per token)**, **KV Cache Memory Footprint**, and **GPU Memory Bandwidth (GB/s)**.

> **A Senior MLE Answer:**
> 
> 
> *"TTFT maps to the Prefill phase—it measures how long the system takes to ingest the prompt and emit token #1. TTFT is dictated by input prompt length (\(N_{\text{prompt}}\)), sequence compute complexity, and available GPU compute TFLOPS. ITL maps to the Decode phase—it measures the delay between each subsequent token. ITL is dictated by model parameter count (bytes per weight), KV Cache memory read overhead, and GPU Memory Bandwidth."*

> *"Temperature \(T\) scales raw logits (\(z_i / T\)) before Softmax normalization. Higher temperatures (\(T>1\)) flatten the probability distribution to increase variance, while lower temperatures (\(0<T<1\)) sharpen it around top tokens. Greedy decoding (\(T \to 0\)) replaces Softmax sampling with a deterministic `argmax`, selecting only the highest-probability token.
